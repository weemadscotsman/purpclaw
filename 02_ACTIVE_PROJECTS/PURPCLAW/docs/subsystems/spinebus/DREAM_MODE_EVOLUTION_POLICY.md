# Dream Mode Evolution Policy

Dream mode is PURPCLAW's offline improvement loop.

It runs when the user is inactive or on explicit command.

It must improve the stack without secretly turning the repo into a goblin parliament.

## Allowed dream tasks

Dream mode may:

- analyze receipts
- compare failed and successful routes
- find repeated manual corrections
- detect unused or broken skills
- detect duplicate tools
- propose faster tool chains
- propose lower-token context packs
- propose skill card updates
- propose registry cleanup
- propose tests
- create patch proposals
- create pull-request-ready diffs

## Forbidden automatic actions

Dream mode must not automatically:

- push to main
- delete user files
- change API keys
- run destructive system commands
- alter tool permissions
- promote unverified lessons
- silently rewrite core prompts
- erase receipts
- bypass approval gates

## Promotion ladder

A learning item moves through:

1. `observation`
2. `lesson_proposal`
3. `replay_tested`
4. `accepted_pattern`
5. `skill_patch`
6. `registry_patch`
7. `mainline_candidate`
8. `promoted`

Promotion requires proof.

## Dream queue item

Each dream task must include:

- id
- createdAt
- source receipt ids
- problem statement
- target subsystem
- proposed improvement
- expected value
- risk level
- approval requirement
- test plan
- output destination

## Value scoring

Prioritize by:

1. revenue potential
2. time saved
3. reduced tool failure
4. reduced token burn
5. faster execution
6. better user output
7. better agent selection
8. clearer receipts
9. reduced maintenance cost

## Output

Dream mode should produce proposals, not vibes.

Accepted outputs:

- markdown patch plan
- JSON lesson proposal
- skill card diff
- registry diff
- test file proposal
- code patch
- receipt analysis

## Rule

Dream mode may sharpen the blade.

It may not swing it without permission.
