## Finding #1 — AntiSkill Loader Threshold Bug → FIXED (Batch 2)

**Symptom:** `skill-loader.loadAntiSkillsForTask(intent)` returned 0 results for AntiSkills just promoted by the same process.

**Root cause (confirmed):**
- `createAntiSkillFromFailure()` sets `score: 0.55`
- Loader filter: `s._rank > 0.05`
- `_rank = overlapScore(qTokens, triggerTokens) * (skill.score || 0.5)`
- For a single-token query (`bad_provider_key`) and a 12-token trigger set: overlap = 1/12 = 0.083
- `_rank = 0.083 * 0.55 = 0.046 < 0.05` → filtered out

**Fix applied (Batch 2, 2026-06-29):**

```js
// In lib/hivemind/skill-loader.js, loadAntiSkillsForTask():
const overlap = overlapScore(qTokens, triggerTokens);
const failureCount = Number(skill.failure_count || 0);
// failure_count boost: 1 fail = 1.0x, 4 fails = 1.5x, 16 = 2x
const boost = 1 + Math.log2(Math.max(1, failureCount)) * 0.25;
const baseScore = Number(skill.score || 0.5);
return { ...skill, _rank: overlap * baseScore * boost };
  // ...
  .filter(s => s._rank > 0.02)  // was 0.05; kind-aware now
```

**Why this is the right fix:**

1. **Kind-aware threshold (0.02 for antiskill, 0.05 for skill):** Asymmetric matching is correct. "Should-match" skills and "should-avoid" AntiSkills serve different purposes. The skill loader is asking "which one of these helps me complete the task?" The AntiSkill loader is asking "which one of these has burned us before?" The latter needs a lower bar to surface.
2. **Failure-count log boost:** Single failures stay quiet (boost=1.0); repeated patterns surface loud (boost grows logarithmically). Matches intuition — "this route has burned us 8 times" is a much stronger avoidance signal than "this route failed once."

**Result after fix:**
- Pattern retrieval: 3/3 ✓
- Per-trace retrieval: 15/15 (100%) ✓
- `avoidance_loop_closes: true` ✓

3. **Loader bug fixes (real, found by the test):**
   - `clamp(n, min, max)` had no default args → `Math.min(undefined, ...)` returned NaN, killing every score. Fixed with `min = 0, max = 1`.
   - `rules.json` had `max_promotable_spring_rank` but the loader read `max_loadable_spring_rank` (different field). Fixed: loader now falls back to `max_promotable_spring_rank` if `max_loadable_spring_rank` is undefined.

4. **Real finding (Batch 4 candidate):** Rank-1 trigger terms grow with verification metadata ("verified", "execution", "adapter", "real", "test", "coverage"), making the overlap-score threshold math marginal for short queries. This is a separate tuning issue, not a launch blocker.
